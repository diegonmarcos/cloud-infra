# PLAN — GHCR as the artifact store: reproducible, pull-not-build CI/CD for every container

Status: **approved 2026-08-25**, implementation in progress (Sonnet agent). Owner of item 6
(cgc-db checkpoints) stays with the cgc-db work; everything else is this plan.

## Why

Measured this week on the real pipeline:

- Every consumer/service image build re-runs `apt-get`, the nodesource script, `npm install`
  and `pip install` inside `Dockerfile.native` (minutes, network-bound, non-reproducible:
  "whatever upstream serves today").
- Every `Ship → <host>` job **builds and deploys in one job over the single shared
  `gha-runner` WireGuard peer slot**; any two concurrent jobs steal each other's mesh
  connection (killed three cgc-db restore-all runs on 2026-08-24).
- Public bases (`busybox`, `alpine/git`, `ubuntu`, `node:22-slim`, the
  `myoung34/github-runner` image) are pulled from Docker Hub anonymously, on the runners and
  on oci-apps itself (restore-all's swap container) — rate-limited and slow, and not pinned.
- `:latest` everywhere at deploy time: a host runs whatever the tag resolves to when it pulls,
  not what the build produced; rollback is "rebuild".
- GHA cache (`actions/cache`) does not exist for a self-hosted fleet runner and is capped at
  10 GB/repo; the fleet cannot run the same workflow with the same warm-up.
- The octocode toolchain image was hand-built once (2026-03-26, 0.12.2) with no builder in this
  repo; that pin rotted for five months. Fixed 2026-08-25 (upstream release, sha256-pinned in
  build.json) — the pattern to generalise.

## Principles (unchanged, enforced)

1. **One universal engine.** Images are built ONLY by `step_docker`
   (`1_cicd/src/scripts/cloud-ship-container-step-build-docker.sh`); deploys ONLY by
   `ship.yml`. `9_others/test/test_no_duplicate_image_builders.sh` forbids a second builder.
   Changing the engine changes the CI/CD of every container in `a_solutions/*/build.json`
   with zero per-service edits.
2. **Pin by version or digest, never `:latest`, for anything that must be reproducible.**
   `:latest` may exist as a convenience alias; nothing *depends* on it.
3. **Data-driven.** Host → runner label, mirror list, base images: all in `config.json` /
   `build.json`. No branching in workflows.
4. **GHA-only builds.** Nothing is built, indexed or served on a desktop; verification of a
   pipeline change is a workflow run and its log.
5. Public packages for tool/runtime images (no project content); private stays private.

## Design

```
build.json (per service)  ──► step_docker ──► ghcr.io/…/<svc>-binaries:<git-sha12> (+ :latest alias)
                                   │  --cache-from/--cache-to type=registry (…:buildcache)
                                   ▼
ship.yml:  Detect changes ──► build (matrix, hosted x86, NO mesh) ──► deploy (per host, needs: build)
                                                                         │ compose pull @digest + up -d
                                                                         │ runs-on: host runner label
                                                                         │ (WireGuard only when no label)
base/tool images (built by the same engine, versioned, multi-arch):
  cgc-runtime:<octocode-ver> = ubuntu:24.04 + node22 + python3/pip/pylance + git + octocode (sha-verified)
  mirrors (weekly): busybox, alpine/git, ubuntu:24.04, node:22-slim, python:3.11-slim, github-runner
```

## Changes, in order (each shippable and testable alone)

### 1. step_docker: registry cache + sha tags + digest output
File: `1_cicd/src/scripts/cloud-ship-container-step-build-docker.sh`
- `docker buildx build … --cache-from type=registry,ref=<image>:buildcache
  --cache-to type=registry,ref=<image>:buildcache,mode=max`.
- Push `<image>:<git-sha12>` in addition to `:latest`; write the pushed digest to
  `$GITHUB_OUTPUT` (`digest_<service>`) and to a small JSON artifact for the deploy stage.
- Keep the old behaviour when buildx is absent (local `build.sh` paths) — degrade, don't fail.

### 3. Compose rendering: deploy by digest
Files: the compose renderer in `cloud-ship-container-engine.sh` (+ the `compose.nix`
convention: `binariesImage`).
- Rendered `docker-compose.yml` references `image@sha256:<digest>` when a digest is supplied
  (deploy stage), else `:<git-sha12>`, else `:latest` (unchanged fallback for local/dagu).
- Deploy = `docker compose pull && docker compose up -d`; rollback = redeploy an older digest.

### 2. ship.yml: split build / deploy
Files: `1_cicd/src/cicd/ship.yml` AND the rendered `.github/workflows/ship.yml` (both — the
rendered copy is what runs; `1_cicd/dist/` is regenerated by the pre-commit hook).
- `build` job: matrix from *Detect changes*, `runs-on: ubuntu-latest`, no WireGuard step, calls
  step_docker, uploads the digest JSON as an artifact.
- `deploy` job per host: `needs: build`, downloads the digests, keeps today's per-host
  concurrency group, runs the compose pull/up. `runs-on` from item 4; the WireGuard step runs
  only when the host has no runner label.
- The 377-hour "Ship → terraform" zombie and "newer pending run evicts older" are why this
  stays ONE workflow with `needs:`, not `workflow_run` chaining.

### 4. config.json: host → runner label
- `vms.<host>.runner_label` (e.g. `oci-apps` → `oci-apps-arm64`, the runners already present).
  Present → local deploy on the host's runner (docker socket, no ssh/rsync/WG). Absent → mesh
  path exactly as today. Data, not workflow logic.

### 5. Base/tool images (versioned, multi-arch, public)
- `cgc-runtime` as a build.json entry (build-only: `enabled`/deploy off) built by step_docker:
  `ubuntu:24.04` + node 22 + python3/pip + pylance + git + octocode fetched by the SAME
  version+sha256 already pinned in `a_solutions/user-ai_cloud-cgc-pub-mcp/build.json`
  `.runtime.octocode.{version,release}`. Then `cloud-cgc-pub-mcp` `native_build.base_image`
  → `cgc-runtime:<ver>` and its `cmd` shrinks to `npm install --omit=dev`.
- `mirror-hermes-image.yml` → `mirror-images.yml`, list-driven from `config.json`
  (`mirrors: [{src, dst}]`), weekly + workflow_dispatch, `imagetools create` (manifest copy,
  multi-arch preserved). Consumers reference the GHCR mirror, never Docker Hub: step_docker
  (busybox for packaging), restore-all (busybox swap), reindex (alpine/git), runner image.

### 6. cgc-db checkpoints as the cache — OWNED BY THE cgc-db WORK, not this agent
- Tag `cgc-db-<repo>:<HEAD12>` + `:latest`; graphrag phase restores the semantic checkpoint of
  the same run so a forced cycle stops embedding every repo twice.

### 7. Tests (`9_others/test/`, POSIX sh, grep-level, dist copy generated by pre-commit)
- step_docker uses the registry cache and tags by sha.
- Rendered deploy compose carries `@sha256:` for every service the deploy stage handles.
- `ship.yml`: build jobs have no WireGuard step; deploy jobs run no `docker build`.
- `config.json` runner labels reference runners that exist (`gh api …/actions/runners`, or a
  static allowlist in config).
- No workflow uses `docker/build-push-action` (existing test, keep green).

## Rollout / canary

1. Items 1 + 3 + 7 land first: behaviour-neutral for deploys (still `:latest` unless a digest is
   supplied), builds just get cached and sha-tagged.
2. Item 2 + 4 land with **no runner label set** → the deploy stage still uses the mesh path;
   verify one full Ship cycle on a small service via workflow_dispatch and read the log.
3. Set `runner_label` for `oci-apps` only; ship one small service; verify `docker compose ps`
   shows the digest; then leave it — every other host is a config flip later.
4. Item 5: `cgc-runtime` first (its consumer is `cloud-cgc-pub-mcp`), mirrors second.

## Non-goals

- No per-service workflows, no `workflow_run` chains, no second image builder.
- No change to build.json's per-service schema beyond the optional `runner_label` on hosts.
- No local builds/indexing on any desktop, ever.

## Risks

- `ship.yml` is every host's deploy path: canary one host + one service, keep the mesh fallback
  data-selected so a bad label can be reverted by config.
- Digest-pinned compose on the box means a `docker image prune` must not remove the pinned
  digest before the next deploy — pin, then prune what isn't referenced (the ship engine's
  reclaim step must read the compose file first).
- Registry cache growth: `mode=max` per image; prune `:buildcache` tags older than N days in
  the weekly mirror workflow.
